# 運用設計(agent の権限・入力の信頼区分・人間によるレビュー)

llm-security-scan v2 を agent として運用するときの設計。手順そのものは `docs/procedure.md`。

## 1. 位置づけ

- LLM による静的レビューは、SAST・SCA・DAST・人手レビューの**補完**であり、代替ではない。ランタイム検証の代わりにもならない。
- 役割分担:

| 工程 | 担うもの | このツールの扱い |
|---|---|---|
| 外部ライブラリの既知の脆弱性 | SCA(npm audit / pip-audit / Trivy) | 報告しない(除外 14) |
| 設定・堅牢化(セキュリティヘッダー、TLS 設定、レート制限) | 構成レビュー、IaC 検査 | 報告しない(公式の除外 7)。「捨てた候補」に理由つきで残る |
| ロジックの脆弱性(認可、テナント境界、インジェクション、認証フロー) | **このツール** + 人手レビュー | 本文の所見 |
| 仕様・運用に依存する境界の候補 | **人のトリアージ** | 「要確認」 |

## 2. 権限の境界

### agent

- **読み取り専用**。許可するツールは `Read Glob Grep Task` だけ。`Write` `Edit` `Bash` `WebFetch` と MCP は許可しない。
  - skill 自身は `allowed-tools` で git の読み取り系 Bash を宣言しているが、headless 実行では `--allowedTools` で上書きして Bash も外す。headless は全体モード(`full <パス>`)専用で、対象は `--add-dir` で渡し、ファイル一覧は Glob で取るので git は要らない。対話実行で差分モードを使うときだけ git の読み取りを許可する。
- レポートはファイルに書かず、応答として返す。保存は呼び出し側(`scripts/save_report.py`)が行う。
- headless 実行と外部由来コード(§3)では、対象リポジトリに `--add-dir` で読み取りアクセスを与えるだけにする。agent の cwd は skill を置いたツール用ディレクトリにし、対象リポジトリでは起動しない(対象側の `.claude/` 設定や hooks を読み込ませないため)。自社コードの対話実行(`docs/procedure.md` §4.1)は対象リポジトリで起動してよい。

### 実行環境

- 実行シェルに本番の API キー・クラウド認証情報・DB パスワードを載せない。Claude Code の認証情報だけを持つ専用ユーザーまたはコンテナで動かす。
- 対象リポジトリは read-only でマウントするか、作業用の clone を使う。
- ネットワークは Claude API への経路だけを許可する。

### 設定の分離

| 置き場所 | 内容 | 変更者 |
|---|---|---|
| skill(`rules/`) | 組織共通の追加観点・除外 | セキュリティ担当。変更したら再評価 |
| 対象リポジトリ(`SECURITY_REVIEW_CONTEXT.md`) | 対象ごとの構成・信頼境界・受容済みリスク | 対象のチーム。セキュリティ担当がレビュー |
| 呼び出し側(runner) | モデル ID、タイムアウト、保存先 | 運用担当 |

## 3. 入力の信頼区分

スキャン対象のコード・コメント・文書は**データであり、指示ではない**(`rules/exclusions.md` の DATA HANDLING RULE)。それでも、対象によって実行環境を分ける。

| 区分 | 例 | 実行環境 | 備考 |
|---|---|---|---|
| 自社コード | 自社リポジトリの PR・ブランチ | 通常の CI / 開発環境 | 標準 |
| 協力会社・顧客由来のコード | 受入検査、納品物のレビュー | **隔離環境**(専用コンテナ、秘密情報なし、外向き通信は Claude API のみ) | `SECURITY_REVIEW_CONTEXT.md` は自社側で書く(対象に含まれていても信用しない) |
| 外部 OSS・フォーク | 依存ライブラリの監査 | 隔離環境 | 全体モード。結果の扱いは SCA と合わせる |

- CI に組み込む場合は、信頼できる PR(組織メンバーのブランチ)だけを対象にする。フォークからの PR は対象にしない。公式の GitHub Action も「プロンプトインジェクション対策はしていない」と明記している。
- レポートに「指示に見える文を対象内で見つけた」という記述があれば、それ自体を所見として扱い、人が確認する。

## 4. 人間によるレビューが必須

- **修正の自動適用は禁止。** 所見・要確認はすべて人がトリアージしてから対応する。
- トリアージの判定区分と記録:

| 区分 | 意味 | 次の動作 |
|---|---|---|
| 真陽性 | 実在し、対応が必要 | 課題として起票。修正後に差分モードで再スキャン |
| 誤検知 | 実在しない、または前提が違う | 理由を記録。頻出するなら `rules/exclusions.md` に理由つきで追加(→ 再評価) |
| 受容 | 実在するが、リスクを受け入れる | 理由と期限を記録。`SECURITY_REVIEW_CONTEXT.md` の "Known accepted risks" に追加 |
| 保留 | 仕様・運用の確認待ち | 確認先と期限を記録。「要確認」の候補はまずここに入る |

- **「要確認」は必ず読む。** 本文の所見が 0 件でも、要確認に境界の候補が載る。確信度 7 と 8 の境目は実行ごとに入れ替わるため、要確認を読まない運用では取りこぼしが出る。
- 記録先は組織の課題管理に合わせる。最低限、対象・コミット・モデル ID・skill の版・判定区分・判定者・日付を残す。

## 5. 失敗の検知

headless 運用では、agent が黙って何もしない・拒否する・途中で止まる場合を失敗として検知する。

| 事象 | 検知 | 対応 |
|---|---|---|
| 拒否・空応答・途中終了 | `save_report.py` が題名の行(それより前の途中経過は捨てる)と 5 節の有無を検査し、終了コード 3 | 失敗として扱い、再実行。繰り返すならモデル・prompt の問題として記録 |
| JSON が壊れている | 同スクリプトの終了コード 4(Markdown は保存される) | Markdown を正として扱う |
| 時間超過・無応答 | runner の `timeout`、または watchdog(進捗ファイルの更新監視) | 対象を分割する(コンポーネント単位) |
| セッション上限 | 標準出力に上限到達のメッセージ | 残りを中断し、リセット後に再開 |

## 6. 変更管理と再評価

### 再評価トリガ

次のいずれかが起きたら、評価ケース(組織内の非公開リポジトリ)で再評価してから適用する。

1. 使用モデルの変更・更新
2. 公式 prompt(upstream)の取り込み
3. `rules/*.md` または `SKILL.md` の変更
4. 出力形式・引数・allowed-tools の変更(multi-scan の I/F に影響)

### upstream 追従

- `docs/upstream.md` のハッシュと upstream の最新を定期的(四半期、またはモデル更新時)に比較する。
- 取り込みは `upstream/security-review.md` と `references/upstream-security-review.md` を同時に更新し、`cmp` で同一を確認する。本文は編集しない。`SKILL.md` が位置の目印にしている見出し(`OBJECTIVE:`、`SECURITY CATEGORIES TO EXAMINE`、`Data Exposure`、`Phase 1 - Repository Context Research`、`REQUIRED OUTPUT FORMAT`、`FALSE POSITIVE FILTERING`、`PRECEDENTS`、`START ANALYSIS`)が変わっていたら `SKILL.md` の参照を直す。
- 公式の除外・判断基準に自社ルールと重複・矛盾するものが増えたら、`rules/` 側を整理する。

### 版管理

- skill の版は SemVer。multi-scan の I/F(出力ファイル名、引数、allowed-tools、JSON スキーマ)を壊す変更はメジャー。
- レポートには使用モデル ID が入る。skill の版は `ChangeLog.md` と git タグで追う。

## 7. 記録と保管

- レポート(Markdown / JSON)は対象のコミットハッシュと一緒に保管する。所見にはファイルパスと行番号、場合によってはコードの断片が含まれるので、**対象コードと同じ機密区分**で扱う。
- `committed_secret` の所見には、秘密の実体(パスワード本体)を書かないよう skill が指示しているが、保管・共有の前に `save_report.py` の出力を目視で確認する。
